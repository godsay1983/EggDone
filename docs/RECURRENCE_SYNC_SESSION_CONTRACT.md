# 规则同步生产会话与配置世代

更新：2026-09-06。阶段：NS5-D2C2B3。两端内容保持一致。

## 本步范围

- 桌面端 `recurrence_sync_session::sync_pair` 与鸿蒙端 `RecurrenceSyncSession.run` 使用生产 Todo/S3、规则传输、合并、快照和版本确认接口。
- 两端设置保存、凭据清除入口接入配置失效标记；主同步入口现已接入规则发现与生产会话，每次同步增加一次规则对象 GET。
- 本步不开放自定义规则 UI，不修改版本号、数据库 schema、签名、实况窗或同步 JSON 格式。
- 主同步已启用规则发现和条件上传，但不代表普通规则操作、备份恢复或真实双端 S3 已验收。

## 规则发现与旧目标兼容

共享用例：`fixtures/recurrence-discovery-v1.json`，共 9 项，两端文件一致。

- 先下载 Todo，再读取本地规则（包含墓碑）并 GET 独立规则对象；不能只看本地是否有规则，否则新设备无法首次发现。
- 本地或远端有规则时走 Todo/规则双文档流程。本地有规则、远端 404 时允许首次条件创建。
- 本地无规则、远端 404 或空规则文档时走原 Todo 流程，不 PUT 空规则文件。
- 仅当本地无规则、远端 Todo 也没有自定义实例候选时，规则 GET 的 403 可降级为旧 Todo 流程，兼容只授权旧 Object Key 的策略。
- 候选指 repeat_series_uuid 非空且 repeat_rule 为空。旧客户端已停止的重复系列也可能符合该形状，此时保守报错而不静默降级；不承诺从 Todo 单独准确识别所有历史系列。
- 有本地规则或远端候选时，403 必须报错；401、网络失败、5xx、非法规则文档均不能当成“没有规则”。有规则的目标必须授权派生规则 Object Key。
- 409/412 按现有条件上传契约处理，双文档流程最多两轮；网络暂时错误交由既有主入口有限重试，配置变更、凭据错误和耗尽的冲突不做网络重试。

## 配置状态

本地 `app_metadata` 使用 `sync.target.epoch.v1`。随机 UUID 只代表当前配置世代，不含 Endpoint、Bucket、Object Key 或凭据，不加入同步文档。

1. 旧库第一次捕获会话时惰性生成 UUID，无需 migration。
2. 校验配置及凭据输入后，先用短事务写入新的 `pending:<UUID>`，再进行外部凭据/配置写入。
3. 同一事务递增 todos、notes、attachments 三个 dirty version 和规则 revision，保留全部领域待同步，清除规则 ETag 和旧成功/错误摘要。
4. 配置写入成功后替换为新的可用 UUID。切换 A→B→A、仅修改凭据或同毫秒重复保存都不能复用旧世代。
5. 写入失败保留 pending，新的规则会话拒绝捕获，旧会话保持失效。用户须重新成功保存；不得恢复旧 UUID。
6. 鸿蒙 AssetStore 分两次写入密钥。中断后再次保存必须重新填写完整的 Access Key / Secret Key，不能凭“两个槽位有值”认定其为一致的一对；也可以先清除凭据再配置。
7. 所有 revision 必须处于安全整数范围；溢出、缺行、事务失败应在外部凭据写入前终止并回滚。无效输入不能使原有效配置失效。

桌面端依赖现有数据库 Mutex 包围配置保存及会话捕获；鸿蒙依赖独立 SyncTargetGate 队列串行化整个配置/密钥写入与捕获。鸿蒙锁顺序为 TargetGate → RecurrenceQueue → 原生短事务，不反向嵌套。

## 会话顺序

- 捕获已完成配置及凭据，构造私有 S3 客户端；调用方不能修改会话内配置。
- 整对下载 Todo 和规则，在两次 GET 之间及返回后确认世代。
- 短本地阶段完成远端合并，再调用 D2C1 原子快照。任一阶段失败不上传、不虚报同步成功。
- Todo 条件 PUT → 检查世代 → Todo 版本 ACK → 规则条件 PUT → 检查世代 → 规则版本 ACK。
- Todo 与规则 ACK 只确认各自捕获的版本；不清除便签、附件或上传期间新修改产生的 dirty。
- 任一条件上传冲突都重跑整对流程，最多两轮。其他错误直接交给调用方处理。
- 收尾检查同一当前快照的两个版本，返回 local_changes_pending；这不是全领域同步成功。
- 数据库事务/Mutex/TargetGate 不跨越网络请求。鸿蒙本地配置保存可以在网络挂起时完成，回包再被世代检查拒绝。

已经发出的 HTTP 请求可能仍在旧目标生效，配置失效标记不能撤回服务器已接收的 PUT。本实现保证其迟到回包不能确认新目标的本地版本，并阻止后续旧会话操作；不承诺撤销远端写入。

## 部分成功与平台边界

- Todo PUT 已确认而规则失败时保留 Todo ACK，规则仍待同步。调用方不能把整个同步记为成功。
- 合并与最终原子快照不是一笔跨网络事务；此前成功的远端合并可保留，后续失败不会伪造上传回执。
- Rust ACK 使用数据库临界区内的短事务；鸿蒙 ACK 使用配置队列与 Repository 的条件更新，配置变更同时递增版本，拒绝旧 ACK。
- Rust 主入口持有 SyncRuntime，覆盖尝试记录、全部领域和最终摘要；内部 Todo 适配不重复获取锁。鸿蒙 SyncService 与 RecurrenceSyncSession 共用 SyncSessionLock，多个服务实例不能同时开始同步。
- 主同步把同一捕获世代传给 Todo/规则、便签、附件上传、元数据与清理。每个可写本地阶段、关键网络边界和成功/失败摘要检查世代，旧回包不得确认新配置或覆盖新目标摘要。
- Todo、便签、附件分别确认实际上传快照版本，不再使用尝试开始时的旧版本。附件存在未上传二进制时，元数据成功也不能清除待同步；规则单独产生并发修改时保留 Todo 聚合待同步提示。
- 桌面端即使部分失败也发送任务/便签刷新事件并刷新托盘；鸿蒙失败路径也重新加载已经落地的合并结果，复用提醒/卡片刷新入口，不能把部分失败标记为全领域成功。
- 主同步写入链路及只读轮询现在都检查配置世代，但它们与按需附件下载不是完整的目标迁移事务；历史远端附件跨 Bucket 搬迁、缓存重建不在本步承诺内。

## B3 独立规则轮询与迟到探测隔离

- 沿用现有前台触发与约 60 秒轮询，追加一次派生规则 Object Key 的 HEAD，不读取正文、不上传、不更新 dirty/同步尝试摘要。不是后台定时保证或实时推送。
- `RemoteSyncState.recurrenceToken`：200 + 有效强 ETag 返回 `etag:<ETag>`；404 返回 `missing`；403 返回 `denied`，不得混同为不存在。401/429/5xx 及缺失、弱或非法 ETag 报错，不推进观察基线。
- 403 探测只表示访问不可用，不是降级授权。首次或探测状态变化触发主同步，由上节 GET 发现策略决定旧目标是否可降级；已有规则不得静默忽略权限错误。
- 规则 token 单独变化即可触发主同步，不依赖 Todo/便签/附件 ETag 变化。无变化时仅做 HEAD；同步失败不消耗该变化，下次合格轮询继续尝试。
- 成功的规则 PUT 回执作为 `ManualSyncResult.recurrenceRemoteToken` 返回；不使用收尾 HEAD 的“最新值”确认规则，否则可能漏掉其他设备在上传后写入的版本。旧 Todo 路径不返回该字段，使用同步前观察值，不做规则写入。
- `RemotePollState` 两端同源逻辑：配置每次重新应用都增加本机 generation 并清规则观察；手动同步/页面隐藏使旧探测失效。旧配置的成功、失败、重试及同步结果不能覆盖新配置的观察值和状态。
- 后端探测捕获完整配置及凭据，在四次 HEAD 之间和最终成功/失败返回时检查同一世代；网络不占数据库/配置队列。鸿蒙探测不修改主同步实例的 targetEpoch。
- 探测 token 仅用于变化比较，不持久化、不写 S3，更不能当作条件上传凭据；所有 PUT 仍必须先下载获得本会话所属的上传令牌。
