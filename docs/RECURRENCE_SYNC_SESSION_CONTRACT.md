# 规则同步生产会话与配置世代

更新：2026-09-06。阶段：NS5-D2C2B1。两端内容保持一致。

## 本步范围

- 桌面端 `recurrence_sync_session::sync_pair` 与鸿蒙端 `RecurrenceSyncSession.run` 使用生产 Todo/S3、规则传输、合并、快照和版本确认接口。
- 两端设置保存、凭据清除入口接入配置失效标记。尚未把新的规则会话接到当前主同步入口，不新增日常规则对象请求。
- 本步不开放自定义规则 UI，不修改版本号、数据库 schema、签名、实况窗或同步 JSON 格式。
- “生产适配器已实现”不等于“已启用生产规则同步”，更不等于真实双端 S3 已验收。

## 配置状态

本地 `app_metadata` 使用 `sync.target.epoch.v1`。随机 UUID 只代表当前配置世代，不含 Endpoint、Bucket、Object Key 或凭据，不加入同步文档。

1. 旧库第一次捕获会话时惰性生成 UUID，无需 migration。
2. 校验配置及凭据输入后，先用短事务写入新的 `pending:<UUID>`，再进行外部凭据/配置写入。
3. 同一事务递增 todos、notes、attachments 三个 dirty version 和规则 revision，保留全部领域待同步，清除规则 ETag 和旧成功/错误摘要。
4. 配置写入成功后替换为新的可用 UUID。切换 A→B→A、仅修改凭据或同毫秒重复保存都不能复用旧世代。
5. 写入失败保留 pending，新的规则会话拒绝捕获，旧会话保持失效。用户须重新成功保存；不得恢复旧 UUID。
6. 鸿蒙 AssetStore 分两次写入密钥。中断后再次保存必须重新填写完整的 Access Key / Secret Key，不能凭“两个槽位有值”认定其为一致的一对；也可以先清除凭据再配置。
7. 所有 revision 必须处于安全整数范围；溢出、缺行、事务失败应在外部凭据写入前终止并回滚。无效输入不能使原有效配置失效。

桌面端依赖现有数据库 Mutex 包围配置保存及会话捕获；鸿蒙依赖独立 SyncTargetGate 队列串行化整个配置/密钥写入与捕获。鸿蒙锁顺序为 TargetGate → RecurrenceQueue → 原生短事务，不反向嵌套。

## 会话顺序

- 捕获已完成配置及凭据，构造私有 S3 客户端；调用方不能修改会话内配置。
- 整对下载 Todo 和规则，在两次 GET 之间及返回后确认世代。
- 短本地阶段完成远端合并，再调用 D2C1 原子快照。任一阶段失败不上传、不虚报同步成功。
- Todo 条件 PUT → 检查世代 → Todo 版本 ACK → 规则条件 PUT → 检查世代 → 规则版本 ACK。
- Todo 与规则 ACK 只确认各自捕获的版本；不清除便签、附件或上传期间新修改产生的 dirty。
- 任一条件上传冲突都重跑整对流程，最多两轮。其他错误直接交给调用方处理。
- 收尾检查同一当前快照的两个版本，返回 local_changes_pending；这不是全领域同步成功。
- 数据库事务/Mutex/TargetGate 不跨越网络请求。鸿蒙本地配置保存可以在网络挂起时完成，回包再被世代检查拒绝。

已经发出的 HTTP 请求可能仍在旧目标生效，配置失效标记不能撤回服务器已接收的 PUT。本实现保证其迟到回包不能确认新目标的本地版本，并阻止后续旧会话操作；不承诺撤销远端写入。

## 部分成功与平台边界

- Todo PUT 已确认而规则失败时保留 Todo ACK，规则仍待同步。调用方不能把整个同步记为成功。
- 合并与最终原子快照不是一笔跨网络事务；此前成功的远端合并可保留，后续失败不会伪造上传回执。
- Rust ACK 使用数据库临界区内的短事务；鸿蒙 ACK 使用配置队列与 Repository 的条件更新，配置变更同时递增版本，拒绝旧 ACK。
- Rust 会话使用现有 SyncRuntime 排他。鸿蒙新会话有独立排他，主入口接入时必须与原有 SyncService 的排他统一，不能让两条同步流程并行。
- 现有主同步仍为旧流程，尚不能声称其全部 GET/合并/ACK 均已受新世代校验保护。本步接入的配置失效标记和版本递增，为后续入口切换提供基础。
