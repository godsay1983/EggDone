# 自定义重复任务：普通操作接入契约

日期：2026-09-06
阶段：NS5-E1（普通完成入口）
状态：完成入口已接通；规则创建 UI 仍关闭。删除/跳过入口、规则 CRUD 和备份恢复属于后续阶段。

## 完成入口

- 桌面端：页面单项、批量、专注窗口按 UUID 完成、系统提醒完成，共用 commands 的事务入口。
- 鸿蒙端：页面单项、批量、通知和卡片共用 TodoRepository；与规则操作使用同一 RecurrenceQueue。
- 两端均在同一个 IMMEDIATE 事务中读取最新任务和规则，不采用调用方持有的旧任务字段决定推进。
- 按 current_todo_uuid 查找非删除、非耗尽规则，交给已有推进事务；任务完成、下一项、规则进度、dirty、实例回执及提醒消费回执原子提交。
- 既有 daily/weekly/monthly/weekdays 继续走原快捷重复算法。当前规则和旧 repeat_rule/其他系列冲突时拒绝整次操作，不同时执行两个算法。

## 幂等与取消完成

- 当前项完成最多生成一个确定性 UUID 的下一计划项；不根据今天日期批量补任务。
- 重复点击/重复通知不再创建下一项、不递增规则 revision。
- 已完成当前项但规则尚未推进时，正常完成入口也可补算一次；提醒入口会要求刷新已落地的规则变化。
- 取消完成只改变该任务，不回退规则、不删除已生成下一项、不重新激活已耗尽规则；再次完成历史项不推进。
- 修改时钟至少大于任务已有 updated_at，防止时钟回拨使取消完成在同步时丢失。
- 通知校验 UUID/提醒时间和本机消费回执；旧通知不能在取消完成后再次完成该任务。
- 已删除、已归档或不存在的任务不推进；规则已结束时保留的任务可普通完成，但不再生成。
- 下一项已存在时保留远端/本机编辑，不覆盖、不重复插入；已删除或归档下一项不重新出现在活动列表。

## 提交后刷新

- 桌面完成结果按 UUID 合并到列表，不直接追加可能已由同步下载的下一项。批量操作按任务分别提交，后项失败时仍展示之前成功项并触发同步。
- 桌面托盘/提醒动作沿用既有数据库刷新和任务变更事件；提醒轮询读取新的任务状态，不承诺进程退出后送达。
- 鸿蒙 TodoStore 重新读取活动列表；通知/卡片协调服务和页面完成共用提交后提醒/卡片刷新。
- 取消已完成项提醒，安排仍未完成且未来到期的提醒；不会调用 cancelAllReminders 干扰专注提醒。
- 系统提醒或卡片刷新失败不回滚任务、不误报完成失败，已有前台/启动恢复流程可重试。
- 批量不是整批原子事务；部分失败时保留错误提示、重新读取已落地数据并刷新提醒/卡片。持久化 dirty 保留，不能把失败当作同步成功。

## 验证边界

- Rust 测试调用实际普通完成和通知事务入口；ArkTS 宿主测试调用生产 TodoRepository、TodoStore 与 ReminderActionCoordinator，数据库/平台依赖由宿主 SQLite 和替身提供。
- 覆盖正常/历史/耗尽/停止、旧提醒、并发队列、关联冲突、时钟回拨、下一项已有/墓碑、阶段写入及提交失败回滚。
- 既有时区/日期/确定性 UUID、事务、快捷重复和同步会话回归继续执行。
- 自动测试、HAP 构建和 LocalTest 不等于原生 RDB/通知/卡片或真实 S3 双端验收。
- 未修改数据库 schema、应用版本、签名配置或实况窗。
