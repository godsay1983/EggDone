# 任务进展记录实现方案

- 日期：2026-10-01
- 状态：设计稿，尚未实现；本轮仅新增文档。
- 范围：EggDone 桌面端与 HarmonyOS 端。
- 代码基线：桌面 1.4.2、鸿蒙 1.5.3；双端数据库 schema 26，数据导出文档最高版本 8。
- 执行顺序：[TASK_PROGRESS_ROADMAP.md](TASK_PROGRESS_ROADMAP.md)。
- 两个仓库保存相同正文；后续修改须同步，不以旧阶段计划覆盖本方案。

## 1. 目标与边界

给一个持续多天的任务留下简短的工作记录，让用户回到任务时知道“做到了哪里、接下来从哪里继续”。

例如任务“完成插件导出功能”下面有两条记录：

- 10月1日 10:20：完成字段映射，还需要测试中文路径。
- 10月2日 16:40：中文路径验证通过，剩余大文件性能测试。

任务备注描述要求，检查清单描述步骤，等待原因解释阻塞，进展记录描述实际推进。这四项独立存在，不相互替换。

首版包括：纯文字记录的新增、查看、编辑、删除，双端同步，备份导入导出，以及随任务生命周期保留或清除。离线也能使用，不需要新的账号、权限、同步空间或手填 Object Key。

首版不做：百分比进度、工时统计、附件、Markdown 编辑器、团队评论、通知、自动操作流水、完整修订历史、AI 总结、记录全文的统一搜索。系统日历仍然只读，不给日程添加此入口。

## 2. 用户操作

### 2.1 入口一致，列表保持紧凑

- 两端任务“更多”菜单加入“进展记录”，放在任务内容类操作附近，与检查清单、关联便签相邻。
- 全部、今天、四象限、日历、等待清单及搜索中的任务，复用同一入口及同一面板。
- 已归档、回收站、关联任务详情提供查看入口；不要只在主列表实现。
- 无记录时不增加主列表标签；有记录时显示紧凑的“进展 N”标签，可进入记录面板。不要单独占一行或增加常驻按钮。
- 数量是有效记录数，不包含删除墓碑。以批量聚合查询获取，不能逐任务查询或逐行发起网络请求。
- 尚未保存的新任务先保存，再添加记录；不允许生成无父任务的本地记录。

### 2.2 面板与布局

标题为“进展记录”，下方显示任务标题。记录按创建时间倒序展示，同一天可共用日期标题，每条显示时间、正文和更多菜单；编辑后追加轻量“已编辑”标识，详细编辑时间按需展示。编辑不改变创建时间和列表顺序。

桌面使用现有对话框规范：顶部任务信息、中间滚动列表、底部输入区；菜单浮层不得被列表或对话框高度裁切。空列表采用紧凑高度，不撑满窗口。

鸿蒙手机使用适合键盘输入的详情面板，平板采用有最大宽度的布局。底部输入区在键盘上方，列表可滚动；不堆叠多排管理按钮。继续使用现有主题 token、文字层级和触控尺寸，不引入新的配色体系。

默认每次加载 30 条，按创建时间与 UUID 组合游标继续加载，避免长记录列表一次性渲染。同步或编辑后重新校验分页边界，列表按 UUID 去重。

### 2.3 新增、编辑、删除

- 输入区提示“记录这次推进了什么…”。首版每条上限 1000 个 UTF-16 code unit，双端计数规则相同。
- 去除首尾空白后必须非空；保留内部换行。纯空白时禁用保存，服务层仍校验，不能误报“本地数据库打不开”。
- 保存以本地事务成功为准，成功后立即显示并清空输入，再走现有自动同步；网络失败不撤销本地记录。
- 保存失败保留输入；关闭有内容的输入区时询问是否放弃。首版草稿仅在当前会话保留，不承诺进程退出后的恢复。
- 每条记录的更多菜单包含“编辑”“删除”。编辑复用输入区并提供取消；删除需要确认，明确只删除这条记录。
- 编辑期间同步带来新版本，保存时检测预期版本，不静默覆盖；保留当前输入并提示重新加载。
- 删除使用墓碑防止旧设备重新带回记录，不提供记录回收站。误删后可重新新增，但使用新 UUID。

## 3. 生命周期规则

| 场景 | 记录行为 |
| --- | --- |
| 未完成、等待中 | 可新增、编辑、删除，不改变等待状态 |
| 已完成但未归档 | 可查看和维护记录，允许补写结果；不会重新打开任务 |
| 重新打开 | 保留原有记录 |
| 归档 | 保留，仅查看；取消归档后恢复维护能力 |
| 移入回收站 | 保留，仅查看；恢复任务后重新按任务状态判断权限 |
| 彻底删除任务 | 清除正文及相关本地缓存；通过既有永久删除终态阻止恢复和迟到同步复活 |
| 复制任务、从模板创建 | 新任务无进展记录，模板不收录实际工作历史 |
| 重复任务生成下一实例 | 不继承，记录只属于原实例，不归属整个重复系列 |
| 更改标题、分组、日期或排序 | 保留，不改变记录内容 |
| 记录先到、父任务尚未同步到 | 保留但隐藏，父任务到达后显示；缺失不等于已删除 |

进展记录有自己的版本和同步状态。写记录不修改任务的完成状态、到期日、今日计划、提醒、任务排序和父任务 updated_at，避免触发无关冲突或重复任务生成。

归档或软删除期间遇到其他设备已经提交的记录，仍合并保存，但保持只读；永久删除终态优先于所有记录写入。

## 4. 数据设计

### 4.1 独立子表

不将记录拼入 Todo.note，也不复用本地便签历史表。便签历史是自动快照、存在本地保留上限；进展是用户主动创建并跨设备同步的数据。

建议新增 task_progress_entries 表，字段如下。名称和编码在 TP-0 固定：

| 字段 | 语义 |
| --- | --- |
| uuid | 记录的跨设备 UUID；创建后不变 |
| task_uuid | 所属任务 UUID；创建后不变 |
| body | 纯文字正文；删除后规范化为空字符串 |
| created_at / created_by | 自动生成的创建时间及设备标识；不可修改，不展示原始设备 ID |
| updated_at / updated_by | 最后修改时间及设备标识 |
| clock | 安全整数范围内的逻辑版本时钟，用于合并，不以墙上时钟决定胜负 |
| deleted_at | 可空；非空表示删除墓碑 |

时间使用 UTC 毫秒，界面按本地时区显示。明确拒绝越界数字、非法 UUID、无效正文、非法时间及未知格式版本，禁止静默截断。

索引至少覆盖 task_uuid + created_at + uuid，以及任务下有效记录的筛选。为乱序同步保留缺失父任务的记录，不能使用会直接丢弃这些数据的外键级联策略。

新增本地同步状态和必要的幂等操作回执，沿用现有模块边界。回执不保留正文副本；请求摘要及结果标识不能进入普通日志。UI 重试复用同一操作 UUID 和记录 UUID，同一操作 UUID 的不同请求必须拒绝。重启后先读取提交结果，不盲目重放新增。

### 4.2 迁移与容量

数据库暂定升级到 schema 27，正式实现前重新检查空闲编号。旧库新增表、索引和同步状态，不转换任务备注，不扫描或改写用户旧正文；新库与旧库走同一 schema 定义。

设计上限暂定：单条 1000 UTF-16 code unit，同步文档最多 20000 条记录（含墓碑）、16 MiB UTF-8。实现时双端共用测试向量固定边界，含中文、emoji 和组合字符。

不自动删旧记录或裁剪墓碑。达到本地容量边界时阻止新增并明确提示；两端合并超过上限时保留本地与远端原数据，不上传截断结果，不显示同步成功。实际文档规模和合并性能在 TP-2 验证，上限变更必须双端同步修改。

## 5. 同步与冲突

### 5.1 复用现有同步，新增独立数据域

建议同步文档为 { format_version: 1, entries: [...] }，自动对象路径为：

    eggdone-progress/v1/<当前有效任务 Object Key 的 UTF-8 SHA-256>/entries.json

参考现有等待处理数据域的自动派生方式，使用同步会话解析后的有效任务路径，不直接读取可能尚未自动切换的旧配置。沿用现有连接、凭据、目标标识和对象路径碰撞检查，不让用户配置此路径。

任务与永久删除终态先合并，再处理进展记录。新数据域要完整接入：本地 dirty、触发自动同步、远端变更检测、有限重试、独立 revision/ACK、ETag 条件写、目标切换隔离和最终 UI 刷新。同步中又写入记录，只确认本次发送的 revision，不能把新修改误标为已同步。

没有记录且从未发现远端对象时不上传空文档；支持无变化时的条件检查。将额外网络请求纳入测量，不新增一套常驻轮询定时器。

首次确认远端不存在可以作为空文档；鉴权失败、网络异常、格式错误不能当空文档。曾见过远端对象后又遇到 404，按现有数据域的防丢失保护处理，不直接重建覆盖。

### 5.2 合并规则

- 不同记录 UUID 取并集；两端离线各新增一条应保留两条。
- 同一 UUID 的 task_uuid、created_at、created_by 必须一致；不一致视为协议错误，拒绝该文档且不改本地副本。
- 未删除记录按 (clock, updated_by, body, updated_at) 确定性比较，设备标识采用规范化 ASCII，正文按 UTF-16 code unit 比较。不依赖系统 locale 或 JSON 字段顺序。
- 每次本地修改从已知版本推进逻辑时钟；溢出明确拒绝，不能回绕。
- 同一 UUID 的删除永久优先于编辑；多个墓碑按固定版本元组决胜，正文统一为空。同 UUID 不允许取消删除，重新记录用新 UUID。
- 永久删除的父任务优先级最高：过滤其所有记录，不再接受正文，不因导入或旧设备上传而复活。

上述合并必须验证交换律、结合律与幂等性。协议固定前要用双端共享向量验证整数边界、Unicode 排序和删除竞争。

首版不是完整编辑历史：两个离线设备同时编辑同一条记录时，只保留确定性胜出的版本，不保证两个正文都保留。正常同步若发现尚未确认的本地编辑被另一版本替代，应给出非阻断提示；当前会话仍有输入时保留，不能无提示清空。保留每次推进的推荐方式是新增记录，而不是反复改写旧记录。

### 5.3 旧版本与目标切换

旧客户端不认识独立对象，不应因其写入任务文档而擦掉进展记录；它也不会展示或备份记录。两端升级后才能完整使用。

旧版发起任务永久删除时，旧版不能清理未知对象；新版收到既有永久删除终态后负责清理进展正文并写回，不能声称旧版已经完成新域的云端清理。

启用、切换同步目标或自动加入空间时，复用既有隔离与恢复流程，不混用旧目标 ETag、ACK 和缓存。所有旧的固定数据域检查/备份/空间切换路径必须纳入新域；无法安全接入的旧路径应明确阻止执行，不能静默漏掉记录，更不能要求用户再做一次手动空间迁移。

## 6. 备份与永久删除

- 版本化 JSON 数据导出暂定升为 v9，新增 task_progress；完整备份内的数据文档也包含该字段，外层容器版本不因本次新增字段自动升级。
- v9 导出始终包含该域，即使为空；v9 缺字段应报格式错误。导入旧版 v8 及更早备份，缺字段表示“不提供此域”，不是删除本地记录。
- 同步更新现有各业务域的备份版本门禁与规范化入口，验证任务、便签、检查清单、模板、今日计划和等待状态在 v9 中仍可往返；不能只让最外层解析器接受新版本。
- 导入复用同步合并规则，并与任务、永久删除终态在同一导入事务内生效；预览展示新增、更新、删除记录数量，失败整体回滚。
- 同步 ACK、目标会话状态及幂等回执不是可移植业务数据，不从另一设备的备份直接恢复。
- 逐条删记录会清空正文，只保留防复活墓碑。父任务永久删除要同步清理进展表、未提交输入、分页/数量缓存和可能含正文的临时导出数据。
- 将记录纳入永久删除前的快照/指纹校验，处理确认删除后、执行前到来的并发新增；不能漏掉新记录，也不能因旧快照误删其他任务数据。
- 新域的清理修订被远端确认前，不宣称云端进展正文已清理；沿用现有后台同步与错误恢复，不给用户增加“同步管理”流程。
- 不承诺擦除用户已导出的文件、对象存储历史版本、第三方备份或数据库介质残留。记录不是端到端加密数据，沿用现有同步安全边界。

## 8. 验证和完成标准

自动化验证覆盖：新旧库迁移、空白输入、Unicode 长度、分页、幂等重试、编辑冲突、离线双向新增、编辑与删除竞争、永久删除后迟到写入、ETag 竞争、目标切换、备份 v8/v9 往返、导入回滚及损坏文档。

界面验收覆盖：桌面所有任务视图即时更新，菜单不裁切；鸿蒙手机/平板、键盘、大字体、浅深主题；空态、长文本、很多记录、保存失败保留输入，以及完成/归档/回收站的操作边界。

必须实测一次“桌面新增，鸿蒙看到；鸿蒙离线新增，恢复同步后桌面看到”，再测试删除与永久删除防复活。使用隔离测试数据和目标，不修改用户实际日程或云端数据；安装设备和真实云端操作另行取得授权。

只有双端 UI、同步、备份、清理和验收全部闭环，才称“任务进展记录完成”。构建通过不能代替双端实际验收；本方案没有预先承诺验收结果。
